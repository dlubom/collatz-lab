# PBI-002: Implement the Checked Rust Reference Engine

- **Status:** Implemented; ready for review
- **Type:** Rust mathematical core and constrained quality gate

## Goal

Create the smallest clear Rust workspace and checked `u128` reference engine
that implements the classical map, finite execution, classical counts, first
descent, and peak semantics with independent examples and a 90% core line-
coverage gate.

## Motivation

The bounded engine is the executable Rust reference against which arbitrary-
precision and later optimized paths are compared. It must favor inspectability,
typed failure, and exact accounting over performance.

## Scope

- Create the root Cargo workspace and pin the Rust toolchain.
- Create `collatz-engine` as a library with `#![forbid(unsafe_code)]`.
- Implement one classical `u128` step using checked odd-branch arithmetic.
- Implement a finite runner with terminal-before-limit ordering, classical
  count, last value, peak, first descent, and typed overflow.
- Implement the pure small Mersenne generator needed by the initial contract.
- Add independent known-value tests for `1`, `2`, `3`, and `27`.
- Add separate tests for even/odd steps, zero, zero limit, peak, and overflow.
- Add property tests for branch formulas and run invariants.
- Establish formatting, Clippy, unit/property tests, core coverage, and a
  constrained mutation gate.

## Out of scope

- `rug`, BigInt, promotion, compressed execution, or optimized jumps.
- CLI, catalogs, controls, JSONL, or research runs.
- Benchmarked optimization, concurrency, SIMD, or GPU.
- A full sequence constant for `27` generated by the tested engine.

## Acceptance criteria

- [x] All production crate roots contain `#![forbid(unsafe_code)]`.
- [x] Zero is rejected before a transition and cannot be constructed as a valid
  domain input without a typed error.
- [x] The even and odd classical branch tests pass independently.
- [x] Inputs `1`, `2`, `3`, and `27` produce `0`, `1`, `7`, and `111` classical
  steps and peaks `1`, `2`, `16`, and `9232` respectively.
- [x] Start `1` terminates before limit checking; a nonterminal zero-limit run
  returns a zero-transition prefix.
- [x] The initial value participates in peak calculation.
- [x] An odd operation beyond the representable threshold reports overflow at
  the current value, does not wrap, and does not increment the count.
- [x] The Mersenne generator maps exponent `5` to `31`.
- [x] Expected known results come from reviewed constants/Lean and not from the
  tested algorithm.
- [x] Rustfmt and Clippy with `-D warnings` pass.
- [x] The mathematical core reaches at least 90% line coverage through the
  deterministic package/lib command.
- [x] Workspace coverage is reported without a global threshold.
- [x] Every material reference-module mutant is killed or documented with an
  accepted classification; test gaps are closed.
- [x] No BigInt, compression, CLI, or experiment functionality is introduced.

## Risks

- A public summary type could conflate overflow with experiment termination.
- An overflow check could occur after arithmetic or after incrementing count.
- Tests could accidentally reproduce implementation logic and cease to be
  independent.
- Coverage could be inflated by execution without meaningful assertions.
- Mutation exclusions could hide weak tests.

## Completion conditions

The exact command evidence, coverage result, mutation classifications, and
independent review are recorded; the living Spec remains aligned; and no
unrequested layer is implemented.

## Independent review

The reviewer manually traces starts `1`, `3`, and an overflow-risk odd value;
checks runner state ordering and error data; verifies test-oracle provenance;
inspects uncovered lines and mutation survivors; and confirms no wrapping or
unsafe escape is possible in project code.

The 2026-08-02 read-only implementation review found no critical issue and
confirmed the map, runner ordering, typed overflow/progress, Mersenne boundary,
independent vectors, coverage repair, and final mutation classification. Its
single important finding was stale lifecycle state in the Spec, Architecture,
and PBI; those documents are aligned in this closure change.

## Refinement protocol

Internal Rust types may be refined while behavior remains identical. Stop and
request human review before changing the map, input domain, terminal priority,
count/peak semantics, overflow result, dependency set, or platform scope.
Observable changes update the living Spec in the same change.
